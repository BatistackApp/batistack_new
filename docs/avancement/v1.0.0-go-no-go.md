# Audit GO / NO-GO 1.0.0

> Document de décision pour la préparation de BATISTACK 1.0.0.
> Mise à jour : 12/11/2026, après fusion des lots 1 à 5 dans develop.

## Décision actuelle

**NO-GO pour la production.** Les lots de stabilisation 1 à 5 ont été intégrés à develop, mais cela ne constitue pas une validation complète de la release ni une autorisation de déploiement.

La CI des PR de lots a exécuté avec succès les contrôles ciblés (qualité/build, intégrité des migrations, régressions paiements/portails/documents, GitGuardian). Les jobs test-global, test-modules et changes étaient ignorés sur les PR ciblant develop. Leur état skipped ne vaut pas réussite.

Le Lot 5 a adapté test-global pour les PR dont la branche cible est production. Ce déclenchement doit être vérifié sur une future PR de release vers production, avant toute fusion de cette PR.

## Éléments techniques à ne pas confondre

- Une CI verte sur une PR ne prouve pas que tous les jobs du workflow ont été exécutés.
- Un test avec mocks ne valide pas la disponibilité réelle d'un fournisseur externe.
- Une migration qui passe sur SQLite ne prouve pas à elle seule sa compatibilité avec le moteur de production.
- Une GitHub Release n'est pas un déploiement serveur.
- Un dump non restauré n'est pas une sauvegarde validée.
- Un rollback du code seul ne garantit pas la compatibilité avec une base déjà migrée.

## Conditions minimales pour décider GO

1. Tous les jobs requis sont exécutés et réussis sur le commit exact candidat.
2. Le test global et les tests modulaires ont une preuve exploitable ; aucun skipped ne doit être présenté comme une réussite.
3. Installation propre et mise à niveau validées sur environnement représentatif.
4. Sauvegarde et restauration complètes testées, avec durée mesurée.
5. Rollback code/base/fichiers testé et documenté.
6. Procédure de déploiement réellement exécutable, sécurisée et répétée en préproduction.
7. Variables, permissions, scheduler, queues, stockage et intégrations vérifiés.
8. Limitations connues et statut de chaque module revus et approuvés.
9. Décision explicite de release par le responsable.

Tant que l'un de ces critères bloquants reste ouvert, la décision demeure **NO-GO**.
